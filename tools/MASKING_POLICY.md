# 열차 민원 개인정보 마스킹 기준 (v2)

## 0. "완벽한 마스킹"의 정의

규칙 기반으로 **자동 유출률 0%는 달성 불가능**하다. 새로운 표기 변형은 항상 규칙을 앞선다.
따라서 이 기준은 "완벽"을 다음과 같이 재정의한다.

> **유출 가능성이 있는 레코드는 자동 통과되지 않는다.**
> 모든 레코드는 마스킹 후 잔존검사를 통과해야 하며,
> 실패한 레코드는 `QUARANTINE` 상태로 격리되어 사람이 검토한다.

즉 목표는 `유출률 = 0`이 아니라 **`무검토 유출률 = 0`** 이다.
이를 위해 설계 원칙을 뒤집는다.

| | v1 (이전) | v2 (현재) |
|---|---|---|
| 기본 태도 | 아는 패턴만 가림 (블랙리스트) | **보존 대상만 남기고 의심은 모두 가림** (화이트리스트) |
| 애매할 때 | 통과 | **마스킹** |
| 놓쳤을 때 | 조용히 유출 | **격리 후 사람 검토** |
| 최적화 지표 | F1 | **유출률 (recall 우선)** |

과마스킹은 분석 품질 손실이고, 미탐지는 법적 사고다. 비용이 비대칭이므로 과마스킹 쪽으로 기운다.

## 1. 3단 분류

### T1 — 직접식별자 : 무조건 완전 마스킹

단독으로 개인을 특정하거나, 외부 시스템 조회로 즉시 특정 가능한 값.

| 항목 | 비고 |
|---|---|
| 이름(한글/영문) | 민원인·동반자·**답변하는 직원 실명 포함** |
| 전화번호 | 휴대·유선·안심번호(050X) |
| 이메일 | |
| 주민등록번호·외국인등록번호 | |
| 여권번호 | |
| 주소 | 도로명/지번 + 동·호수 |
| 카드번호·계좌번호 | |
| 회원번호 | 조회 시 전체 개인정보 노출 |
| 사번 | 직원 식별자 |
| 생년월일 | |
| 복지카드번호 | **장애 정보 추론 → 민감정보** |
| 차량번호 | |
| IP주소 | |
| 소속(학교·회사명) | 이름과 결합 시 특정 가능 |
| 아동 나이 | 미성년자 정보 |

### T2 — 준식별자 : 조합 재식별 차단 목적 마스킹

단독으로는 개인정보가 아니지만, 다른 축과 결합하면 1명으로 수축한다.

| 항목 | 판단 |
|---|---|
| 예약번호·승차권번호 | **마스킹.** 발권 시스템 조회로 즉시 개인 특정 → 실질 직접식별자 |
| 좌석번호 (`7호차 12A`) | **마스킹.** `열차번호 + 운행일 + 좌석` = 전 세계 1명 |
| 호차 단독 (`3호차`) | 보존. 좌석 없이는 수백 명 단위 |

**설계 판단 — 조합 위험은 보존가치가 가장 낮은 축에서 끊는다.**

`열차번호 × 운행일 × 좌석번호` 3축이 결합해 재식별이 일어난다.
이 중 열차번호와 운행일은 민원 분석의 핵심 축(노선별·시간대별 민원 예측)이므로 가리면 데이터가 죽는다.
좌석번호는 분석 가치가 거의 0이다. **따라서 좌석번호만 가려 조합을 끊는다.**
그 결과 `KTX 101 / 10월 23일`로 좁혀도 집합 크기는 좌석 수(약 900석)만큼 남아 k-익명성이 확보된다.

### T3 — 운영정보 : 마스킹 금지 (SHIELD)

마스킹하면 민원 분석 자체가 불가능해지는 값. 규칙보다 **우선 선점**해 보호한다.

열차번호·열차명 · 역명 · 운행일시 · 지연시간 · 지연율(%) · 금액 · 호차 단독 ·
대표번호(1544-7788 등) · 부서명 · 오류코드 · 앱 버전 · 인원수·좌석수·점수

## 2. 우선순위 (충돌 해소)

같은 글자를 두 규칙이 다르게 판정할 때 숫자가 큰 쪽이 이긴다.

| 우선 | 레이어 | 예 |
|---|---|---|
| **120** | 라벨 문맥 식별자 | `사번 19870` — 5자리라 구조만으로는 못 잡음 |
| **110** | 과거연도 날짜 | `1978년 4월 12일` → 민원의 운행일은 항상 최근 ⇒ 생년월일 |
| **105** | 좌석번호 | `7호차 12A` — 호차 SHIELD를 덮어써야 함 |
| **100** | **SHIELD (T3 보존)** | `1544-7788`을 전화번호 규칙보다 우선 보호 |
| 90 | 구조적 직접식별자 | 주민번호·전화·이메일·카드·여권·차량·IP |
| 80 | 도메인 준식별자·소속·나이 | 예약번호·승차권번호·학교명 |
| 70 | 이름 (라벨·호칭 문맥) | `담당자 ○○○`, `○○○ 고객님` — **성씨 사전 불필요** |
| 60 | 이름 (성씨사전 + 조사) | `강민호가` |
| **30** | **FAIL-SAFE** | SHIELD 안 걸린 7자리 이상 숫자는 전부 가림 |

우선순위 30의 FAIL-SAFE가 이 기준의 핵심이다.
`사번`·`예약번호`·`보관번호`처럼 미리 모르는 번호 체계가 전부 여기서 잡힌다.
SHIELD로 보존 대상을 먼저 확정했기 때문에 공격적으로 가려도 운영정보는 살아남는다.

## 3. 이름 규칙의 전환

v1은 성씨 사전(80개)에 의존했다. 희귀 성씨·외국인·오탈자에서 전부 뚫린다.
v2는 **문맥이 확실하면 성씨 사전을 보지 않는다.**

```
확실한 문맥  →  사전 무시, 2~4음절 한글 어절이면 마스킹
  라벨:  성명/이름/예금주/수취인/신청인/민원인/담당자/인솔교사/보호자 + ○○○
  호칭:  ○○○ 고객님/님/씨/귀하/과장/기사님/역장님

애매한 문맥  →  성씨 사전 + 조사 경계 (v1 방식, 보조 수단)
```

`남궁민수`(복성), `HONG GILDONG`(영문) 모두 문맥 규칙으로 처리된다.

## 4. 민원–답변 쌍 일관성

동일 인물이 민원과 답변에 모두 등장한다. 쌍 단위로 **같은 토큰**을 부여한다.

```
민원: {{이름}} → <이름_1>      답변: {{이름}} → <이름_1>   (동일 인물)
                                     담당직원  → <이름_2>   (다른 인물)
```

레코드 간에는 토큰을 공유하지 않는다 (교차 연결 방지).

## 5. 출력 모드

| 모드 | 결과 | 용도 |
|---|---|---|
| `label` | `[이름]` | 외부 공개·학습데이터 (복원 불가) |
| `token` | `<이름_1>` + 매핑표 | **중복 민원 탐지·분석** (가명처리, 매핑표 분리보관 필수) |
| `partial` | `010-****-5678` | 상담원 확인용 |

팀의 "동일 민원 3건 중첩 알림"에는 `token` 모드가 필요하다.
`label`은 동일인 구분이 불가능하다.

## 6. 운영 게이트

```
마스킹 → 잔존검사 → PASS      → 분석 파이프라인
                  → QUARANTINE → 사람 검토 큐
```

QUARANTINE 트리거

| 검사 | 잡는 것 |
|---|---|
| 연속숫자 7+ / 숫자군 | 미처리 번호 |
| `@` / `01X` 흔적 | 미처리 연락처 |
| 호칭 앞 미마스킹 어절 | 미처리 이름 |
| 영숫자 혼합 10자+ | **모르는 번호 체계** (`TKT7A9F2B4C8D1E6`) |
| 분절 숫자열 | **공백으로 쪼갠 전화번호** (`0 1 0 2 3 4 …`) |
| 우회표기 | `gildong dot hong at gmail dot com` |
| 라벨 뒤 미마스킹 | **라벨만 보고 유출 판정** — 규칙이 모르는 성씨·표기도 잡힌다 |
| 영문 레코드 (영문 4단어+) | 한글 규칙은 영문 성명을 못 가린다 → 전량 사람 검토 |

잔존검사는 마스킹 토큰을 가린 뒤 수행한다. 그러지 않으면 `[이름]이고`의 "이름"을
라벨로 읽어 자기 자신을 격리한다 (실제로 발생한 버그).

## 7. 운영자가 관리해야 하는 입력 2개

코드가 아니라 **설정**이다. 이 두 개가 비면 기준이 작동하지 않는다.

### `OFFICIAL_NUMBERS` — 공식 대표번호 화이트리스트

**정규식으로는 공식 번호와 개인 번호를 구분할 수 없다.**
`1544-7788`(고객센터)과 `053-123-4567`(담당자 직통)은 같은 전화번호 모양이다.
직원 '직통' 번호는 개인에 귀속되므로 절대 넣지 않는다.
여기에 없는 모든 전화번호는 개인 연락처로 간주해 마스킹한다.

### `NAME_STOP` — 이름 부정 사전

성씨 사전 기반 규칙(prio 60)의 정밀도는 전적으로 이 사전이 결정한다.
`주말에도`·`연락처`·`계정은` 전부 성씨로 시작하는 평범한 명사다.
실데이터 오탐을 보며 계속 늘려야 하고, **이것이 규칙 기반 운영 비용의 본체다.**

## 8. 측정 결과 (합성 데이터 18쌍 / 마스킹 대상 62건 / 보존 대상 89건)

| 지표 | FAIL-SAFE OFF | **FAIL-SAFE ON** |
|---|---|---|
| **유출률** | 8.07% (43/533자) | **0.00% (0/533자)** |
| 보존 훼손률 | 0.00% | **0.00%** |
| 과마스킹 | 0.16% (4/2577자) | **0.16% (4/2577자)** |
| 스팬 재현율 | 91.94% (57/62) | **100% (62/62)** |
| 게이트 | PASS 17 / 격리 1 | PASS 17 / 격리 1 |

FAIL-SAFE OFF 에서 유출된 5건이 이 설계의 근거다.

- `5412-7534-1122-3456` — **Luhn 검증 때문에** 카드 규칙이 거부
- `110-234-567890` — 은행명이 계좌번호 뒤에 와서 문맥 규칙 불일치
- `윤서연` / `조현우` — 조사도 호칭도 없이 연락처 앞에만 놓인 이름
- `남궁민수` — 쉼표 나열 안의 복성

앞 2건은 FAIL-SAFE 숫자 규칙이, 뒤 3건은 2차 패스 **근접확산**이 잡는다.

> **주의** — 위 수치는 이 합성 데이터에 맞춰 튜닝된 값이므로 상한선으로만 봐야 한다.
> 실데이터 적용 시 민원 200건을 라벨링해 7:3으로 나누고, 학습분으로만 사전을 튜닝한 뒤
> 검증분에서 측정한 값이 진짜 성능이다.

## 9. 법적 구분

가명처리(추가정보 분리보관 시 통계·연구 활용 가능)와 익명처리(복원 불가)는 다르다.
`token` 모드의 **매핑표가 곧 '추가정보'** 이므로 원본 데이터와 분리해 암호화 보관해야 한다.
실제 적용 전 사내 개인정보보호 담당자 검토가 필요하다. 본 문서는 법률 자문이 아니다.

> 법적 구분: 가명처리(추가정보 분리보관 시 통계·연구 활용 가능)와 익명처리(복원 불가)는 다르다.
> 실제 적용 전 사내 개인정보보호 담당자 검토 필요. 본 문서는 법률 자문이 아니다.
